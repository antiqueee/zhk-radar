# Радар проблемных ЖК — ТЗ и архитектура

Nov 10, 2026 · @alex

## 1. Суть проекта

«Радар» (рабочее название) — внутренний инструмент агентства. Раз в неделю он находит жилые комплексы, где назревает или уже идёт конфликт с покупателями, и готовит по каждому расклад: что болит у жителей и с каким предложением идти к девелоперу.

**Какую задачу решает.** Агентство само ищет клиентов, а не клиенты его. Поиск сейчас ручной: аналитик гуглит, читает чаты и записывает выводы в таблицу. Продукт забирает на себя сбор, сверку и черновик расклада. Человеку остаются решение «идём или нет» и сама продажа.

**Кто пользуется.** Два руководителя агентства, оба с полным доступом. Ролей и разграничения прав нет. Третий участник — оператор (на старте это разработчик), он следит за рабочим Telegram-аккаунтом и чинит сборщики.

**Три слоя работы:**

1. **Радар.** Еженедельный обход открытых источников: реестры, надзор, суды, СМИ, отзывы. Результат — обновлённый реестр объектов и список изменений за неделю.
2. **Чаты.** По объектам из топа система находит открытые чаты жителей, рабочий аккаунт вступает в них, переписка загружается и разбирается по темам.
3. **Расклад.** По объекту собирается диагноз (стадия кризиса, главные боли, ближайшие даты) и предложение из библиотеки услуг агентства, привязанное к этим болям.

**Три выхода:**

- **Telegram-бот** — дайджест по понедельникам, кнопки решений, внеплановые сигналы, запрос по объекту.
- **Google Таблица** — полный реестр, который можно фильтровать и сортировать.
- **PDF на две страницы** — расклад по одному объекту с УТП.

**Как понять, что продукт работает.** Главная метрика — сколько объектов из дайджеста руководители взяли в работу и сколько из них дошло до встречи с девелопером. Вспомогательные: доля объектов, отмеченных «не интересно» (качество отбора), и доля раскладов, где проверка перед КП нашла ошибку (качество данных).

**География.** Первый приоритет — Москва, Московская область, Санкт-Петербург, Ленинградская область. Остальная Россия идёт вторым блоком дайджеста, не больше трёх объектов в неделю.

**Что в продукт не входит:**

- Закрытые чаты и чаты, где для входа нужно подтверждать ДДУ. Только открытые.
- Любые действия в чатах. Рабочий аккаунт только читает и никогда не пишет.
- Автоматическая отправка писем и КП девелоперам. Продукт готовит материал, отправляет человек.
- Ежедневный мониторинг для действующих клиентов. Это отдельная система агентства; «Радар» работает до продажи.
- Имена и ники жителей в дайджесте, таблице и PDF. В выдаче только темы, частоты и цитаты без автора.

**Словарь, чтобы дальше читать без запинок:**

| Термин | Значение |
| --- | --- |
| Объект | Один корпус (дом) с собственным ID в ЕИСЖС. Не весь ЖК: у корпусов одного ЖК разные сроки и разный статус |
| ЕИСЖС | Единая информационная система жилищного строительства, сайт наш.дом.рф. Официальные проектные декларации и сроки по каждому дому |
| ЕРЗ | Единый ресурс застройщиков, erzrf.ru. Рейтинги застройщиков, в том числе по объёму переносов |
| ПД | Проектная декларация. В ней плановый срок ввода и срок передачи квартир |
| РВЭ | Разрешение на ввод в эксплуатацию. Дом достроен юридически |
| ЗОС | Заключение о соответствии от стройнадзора. Нужно для получения РВЭ |
| ДДУ | Договор долевого участия. Срок передачи квартиры в нём — юридически значимая дата |
| Сигнал | Одно проверяемое событие по объекту: перенос срока, публикация, предостережение надзора, иск, всплеск в чате |
| Расклад | Итоговый документ по объекту: диагноз плюс предложение |
| Оффер | Одна услуга из библиотеки агентства с условиями, когда её предлагать |
| Стоп-лист | Девелоперы и объекты, к которым не идём: действующие клиенты, партнёры, отказники |

## 2. Недельный цикл глазами пользователя

Руководитель тратит на продукт 10–15 минут в понедельник и по паре минут на каждый расклад. Всё остальное делает система и оператор. Время везде московское.

| Когда | Что делает система | Что делает человек | Что получается |
| --- | --- | --- | --- |
| Вс 22:00 – Пн 07:00 | Радар-прогон: обходит источники, обновляет реестр, считает скоринг, для новых объектов из топа заранее ищет открытые чаты | Ничего | Свежий реестр и список изменений |
| Пн 09:30 | Бот присылает дайджест: 3–5 объектов по приоритетным регионам и до 3 по остальной России | Руководитель читает и под каждым объектом жмёт одну из кнопок: «Подключить чаты», «Расклад», «Позже», «Не интересно» | Решение по каждому объекту |
| Пн – Вт | Ставит одобренные чаты в очередь. Рабочий аккаунт вступает, не больше пяти чатов в сутки. Загружается история за 90 дней | Оператор вступает вручную там, где нужна капча или заявка | Чаты подключены, бот отчитывается по каждому |
| Ср 10:00 | Собирает предварительный расклад по истории чатов и кабинетным данным, делает PDF | Руководитель читает PDF, жмёт «Взять в работу» или «Не интересно» | Расклад v1: срез на сегодня |
| Ср – Вс | Каждую ночь дочитывает новые сообщения в подключённых чатах. При резком событии шлёт внеплановый сигнал | Ничего, если нет сигнала | Накапливается динамика |
| Следующий Пн | В новом дайджесте отдельный блок «В работе»: что изменилось за неделю по взятым объектам. Расклад пересобирается с динамикой | Руководитель решает, идти ли к девелоперу. Кнопка «Готовим КП» запускает версию для клиента | Расклад v2: срез плюс тренд |

**Почему расклад приходит в среду, а не через неделю.** В большинстве открытых чатов история доступна сразу после входа. Ждать неделю, чтобы «насканировать» переписку, не нужно: за 90 дней истории видно больше, чем за 7 дней наблюдения. Вторая неделя нужна только для тренда — растёт напряжение или спадает.

**Статусы объекта, которые видит руководитель:**

1. **Новый** — впервые попал в дайджест.
2. **Чаты в очереди** — одобрено подключение, идёт вступление и загрузка.
3. **Расклад готов** — PDF отправлен.
4. **В работе** — руководитель решил идти к девелоперу.
5. **КП отправлено** — отмечается вручную кнопкой.
6. **Встреча** — отмечается вручную.
7. **Закрыт** — с причиной: стал клиентом, отказ, неактуально.
8. **Отложен** — вернётся в дайджест через четыре недели или при новом сигнале.
9. **Не интересно** — больше не показывается; причина сохраняется и учитывается в скоринге.

**Внеплановые сигналы.** Бот пишет вне расписания только в четырёх случаях, чтобы не превратиться в шум:

- по объекту «в работе» вышла публикация в федеральном или крупном региональном СМИ;
- срок ввода или передачи прошёл, а разрешения на ввод нет;
- в подключённом чате число сообщений за сутки втрое выше среднего за 30 дней и тема — конфликт;
- в чате появился шаблон коллективной жалобы, сбор подписей или призыв к акции.

## 3. Архитектура

Система — один конвейер на Python вокруг PostgreSQL. Он живёт на двух серверах: основной в Европе и маленький шлюз в России. Причина разделения простая: моделям и Telegram нужен европейский адрес, а части российских сайтов — российский.

Сборщики и читатель чатов только кладут данные в базу. Всё, что видят руководители, строится из базы, поэтому любой вывод можно проследить до источника.

### Почему два сервера

| Что | Откуда доступно | Где запускаем |
| --- | --- | --- |
| OpenRouter и модели | Из России доступ к западным моделям ненадёжен, а оплата российской картой, скорее всего, не пройдёт | Европа |
| Telegram (чтение чатов и бот) | В России замедляется с февраля 2026 года, работает с перебоями | Европа |
| наш.дом.рф, сайты надзора и прокуратуры, часть региональных СМИ | Часть ресурсов не отвечает зарубежным адресам | Россия, через шлюз |
| Yandex Search API | API облака, должно работать отовсюду; проверить на этапе 0 | Европа, при проблемах — через шлюз |
| Google Sheets API | Из Европы без ограничений | Европа |

Российский шлюз — это не второй экземпляр системы, а обычный HTTP-прокси с паролем, который принимает запросы только с адреса основного сервера. Данные на нём не хранятся.

### Компоненты

| Компонент | Что делает | Вход → выход |
| --- | --- | --- |
| Планировщик | Запускает прогоны по расписанию и по командам из бота | Расписание → записи в `runs` |
| Сборщик реестров | Забирает карточки домов из ЕИСЖС и рейтинги ЕРЗ | Сайты реестров → `objects`, `object_snapshots`, `developers` |
| Поисковый сборщик | Гоняет запросы через Yandex Search API, скачивает найденные страницы | `watch_queries` → `documents` |
| Сборщик каналов | Читает публичные каналы надзора и профильных СМИ | Список каналов → `documents` |
| Экстрактор | Модель читает документ и вынимает факты с цитатами | `documents` → черновики сигналов |
| Сопоставитель | Понимает, к какому девелоперу, ЖК и корпусу относится факт; склеивает дубли | Черновики → `signals` |
| Скоринг | Считает три оси, стадию, класс; применяет правила раннего предупреждения | `signals`, `objects` → оценки в `objects` |
| Исследователь | Модель с веб-поиском добирает недостающее по объектам из топа | Вопросы по объекту → `documents`, `signals` |
| Поиск чатов | Ищет открытые чаты ЖК | `complexes` → `chats` со статусом «найден» |
| Читатель чатов | Рабочий аккаунт: вступает, грузит историю, дочитывает новое | `chats` → `messages` |
| Разметчик | Модель ставит каждому сообщению тему, тон и флаги | `messages` → `message_labels`, `chat_topic_daily` |
| Сборщик расклада | Собирает боли, подбирает офферы, пишет текст, отдаёт на проверку второй модели | `signals`, `pains`, `offers` → `briefs` |
| Генератор PDF | Верстает расклад в две страницы | `briefs.payload` → файл PDF |
| Бот | Дайджест, кнопки, карточки, сигналы, команды оператора | База ↔ руководители |
| Экспорт в таблицу | Перезаписывает листы Google Таблицы, читает лист «Стоп-лист» | База → таблица |
| Шлюз моделей | Единая точка вызова OpenRouter: роли, повторы, лимит бюджета, журнал | Вызовы из кода → `llm_calls` |
| Наблюдение | Следит, что прогоны прошли, сборщики живы, деньги не кончились; пишет оператору | `runs`, `sources` → сообщения оператору |

### Шаги недельного прогона

1. **Реестры.** Обновить карточки домов по четырём приоритетным регионам и по объектам, которые уже в реестре. Сравнить с прошлым слепком. Каждое изменение срока превращается в сигнал.
2. **Правила.** Прогнать R1–R7 по всем домам.
3. **Поиск.** Выполнить поисковые запросы, отбросить уже известные ссылки, скачать новые страницы.
4. **Каналы и ленты.** Забрать новое из каналов надзора, новостей прокуратуры, профильных СМИ.
5. **Извлечение.** По каждому новому документу модель возвращает список фактов в JSON: что произошло, с кем, когда, дословная цитата.
6. **Проверка цитат и привязка.** Код проверяет, что цитата есть в тексте. Сопоставитель привязывает факт к объекту.
7. **Скоринг.** Пересчитать оценки и классы.
8. **Добор.** Для 15–20 лучших кандидатов исследователь отвечает на конкретные вопросы: получено ли РВЭ, был ли ответ застройщика, кто руководит клиентским сервисом.
9. **Повторный скоринг** и отбор в дайджест.
10. **Поиск чатов** для новых объектов классов A, B и «Ранний».
11. **Сборка дайджеста**, экспорт в таблицу, отправка в 09:30.

Каждый шаг пишет свой результат в базу и может быть перезапущен отдельно. Если шаг упал, следующие работают на том, что есть, а в дайджесте появляется строка «источник N на этой неделе не обновлён».

### Главный принцип: модель читает, код считает

- Всё, что можно посчитать без модели, считается кодом: даты, разницы, числа сообщений и авторов, баллы, правила.
- Модель делает три вещи: вынимает факты из текста, размечает сообщения, пишет текст расклада.
- Модель никогда не является источником факта. Факт — это строка в `signals` со ссылкой на документ и цитатой. В презентации агентства это названо «доказательной аналитикой», и продукт обязан этому соответствовать.

### Что проверено, а что нет

- **ЕРЗ проверен.** Страница рейтинга отдаётся обычным HTML, колонки с переносами на месте, по 20 строк на страницу, срез на 01.11.2026 уже опубликован. В карточках ЖК на ЕРЗ есть только «Срок сдачи по ЖК» с точностью до квартала, готовности в процентах там нет.
- **ЕИСЖС нужно проверить на этапе 0.** Это главный источник по корпусам, и от него зависят правила раннего предупреждения. Надо открыть каталог новостроек и карточку дома в браузере, посмотреть запросы на вкладке «Сеть» и записать: адреса запросов, какие поля приходят, есть ли в ответе готовность и история сроков, отвечает ли сайт зарубежному адресу.
- **Если готовности в процентах в ЕИСЖС нет,** правила R1 и R5 отключаются, остальные пять работают на датах. Готовность тогда оценивает исследователь по странице «ход строительства», только для топа.
- **Список каналов и сайтов надзора** по четырём регионам собрать вручную на этапе 0 и записать в `config/sources.yaml`. Из ручных таблиц уже известен канал Мосгосстройнадзора.

### Поисковые запросы

Запросы лежат в таблице `watch_queries` и делятся на три группы.

**Общие по региону** (ищут новые объекты, которых ещё нет в реестре). Подставляется каждый из четырёх регионов и крупные города областей:

- `дольщики жалуются перенос сроков {регион}`
- `задержка выдачи ключей новостройка {регион}`
- `дольщики коллективное обращение застройщик {регион}`
- `дольщики обратились в прокуратуру ЖК {регион}`
- `стройнадзор предостережение застройщику {регион}`
- `иски к застройщику неустойка дольщики {регион}`
- `стройка остановлена ЖК дольщики {регион}`
- `жители новостройки жалуются управляющая компания {регион}`
- `новостройка жители жалуются отопление лифты протечки {регион}`
- `смена застройщика достройка ЖК {регион}`

**По девелоперу** (для всех, у кого доля переносов по ЕРЗ выше 20%): `{девелопер} перенос сроков`, `{девелопер} дольщики`, `{девелопер} жалобы жителей`.

**По ЖК** (для объектов от класса «Наблюдение» и выше): `ЖК {название} перенос`, `ЖК {название} дольщики`, `ЖК {название} жалобы`.

Каждый запрос идёт с сортировкой по дате и ограничением «за последние 14 дней», чтобы не тащить старое. Ожидаемый объём — около 1 000 запросов в неделю. Способ ограничить дату в Yandex Search API (оператор в тексте запроса или параметр) уточнить по справочнику API на этапе 0.

### Правила скачивания страниц

- Один запрос к одному сайту не чаще чем раз в 2–3 секунды. Уважать `robots.txt`.
- Сначала простой HTTP-запрос. Если текст статьи не извлёкся — повтор через Playwright.
- Российские государственные сайты и всё, что вернуло ошибку доступа, идут через российский шлюз.
- Снимок страницы сохраняется на диск. Новости и карточки меняются и исчезают, а снимок — это доказательство, на котором стоит сигнал.
- Уже скачанный адрес повторно не скачивается, кроме карточек реестров.

## 5. Модели и поиск

Для российского рынка важнее не модель, а поисковик: ищем Яндексом, читаем моделью. Из двух названных моделей основным исследователем берём Gemini 4 Argon. GPT-6 Astra на старте не нужна: она в пять раз дороже, а узкое место не в уме модели. Цены и слаги ниже — со страниц OpenRouter на 10 ноября 2026 года.

### Почему нельзя просто включить веб-поиск у модели

- У OpenRouter [пять поисковых движков](https://openrouter.ai/docs/guides/features/server-tools/web-search): встроенный поиск провайдера (`native`), Exa, Parallel, Firecrawl и Perplexity. Яндекса среди них нет.
- Региональные российские порталы, отраслевые сайты, отзывы и форумы западные индексы видят хуже Яндекса. Это моя оценка, а не измерение; её проверяет прогон из конца раздела.
- Параметр страны `user_location` работает только у встроенного поиска провайдера. Параметра языка нет вообще.
- В списке моделей Google со встроенным поиском документация называет семейство Gemini 3. Есть ли он у Argon, нужно посмотреть по значку Web Search на странице модели. Если нет, поиск молча уйдёт в Exa.
- Модель с поиском каждый раз ищет по-разному. Для еженедельного сравнения «что изменилось» нужен повторяемый процесс: одни и те же запросы, один и тот же поисковик.

### Два уровня поиска

**Уровень 1, основной: Yandex Search API и собственное скачивание.** Код гоняет шаблоны запросов из раздела 4, получает ссылки, сам скачивает страницы и отдаёт текст модели-экстрактору. Модель здесь не ищет, а только читает.

| Параметр Yandex Search API | Значение |
| --- | --- |
| Адрес | `POST https://searchapi.api.cloud.yandex.net/v2/web/search` |
| Авторизация | API-ключ сервисного аккаунта с ролью `search-api.webSearch.user`, плюс `folderId` |
| Регион | `225` — Россия |
| Цена, отложенные запросы | 30,5 ₽ за 1 000 (ночью 25,41 ₽) |
| Цена, синхронные запросы | 488 ₽ за 1 000 днём, 366 ₽ ночью |
| Ограничения | Запрос до 400 символов и 40 слов; отложенные запросы принимаются только с 00:00 до 06:00 по Москве, результат хранится до 12 часов |

Ночное окно отложенных запросов совпадает с временем радар-прогона, поэтому весь недельный объём идёт по дешёвому тарифу. Синхронные запросы нужны только для команды «проверь объект сейчас» из бота. Источники: [тарифы](https://aistudio.yandex.ru/ru/docs/search-api/pricing), [лимиты](https://aistudio.yandex.ru/ru/docs/search-api/concepts/limits), [быстрый старт](https://yandex.cloud/en-ru/docs/search-api/quickstart/v2).

**Уровень 2, точечный: модель-исследователь с веб-поиском.** Только для 15–20 объектов из топа и только на конкретные вопросы, на которые шаблоны не ответили. Исследователь получает два серверных инструмента OpenRouter и третий свой:

```json
{
  "model": "google/gemini-4-argon",
  "tools": [
    {"type": "openrouter:web_search",
     "parameters": {"max_results": 8, "max_total_results": 40,
                    "user_location": {"type": "approximate", "country": "RU"}}},
    {"type": "openrouter:web_fetch"},
    {"type": "function", "function": {"name": "yandex_search", "description": "Поиск в Яндексе по России"}}
  ],
  "max_tool_calls": 20
}
```

Третий инструмент, `yandex_search`, — наша собственная функция поверх синхронного Yandex Search API. Так исследователь может искать и западным индексом, и Яндексом, а мы видим, какой из них дал результат. Цена поиска OpenRouter: Exa 0,007 $ за запрос, Parallel 0,005 $, Perplexity 0,005 $, встроенный — по тарифу провайдера. Скачивание страниц движком OpenRouter бесплатное, до 50 за запрос.

### GPT-6 Astra или Gemini 4 Argon

|  | [GPT-6 Astra](https://openrouter.ai/openai/gpt-6-astra) | Gemini 4 Argon |
| --- | --- | --- |
| Слаг | `openai/gpt-6-astra` | `google/gemini-4-argon` |
| Цена, вход / выход | 10 / 50 $ | 2 / 10 $ |
| Контекст | около 1,05 млн токенов | около 1,05 млн токенов |
| Индекс Artificial Analysis | 56,9 | 50,4 |
| Вышла | начало сентября 2026 | 13 октября 2026 |

- **Argon — да, основным исследователем.** Задача исследователя — много читать и аккуратно выписывать. Для этого важны цена входных токенов и размер контекста.
- **Astra — нет, пока прогон не докажет обратное.** При недельном доборе по 20 объектам разница в цене — десятки долларов в месяц, это терпимо. Но брать её стоит, только если она находит то, что Argon пропускает.
- **Цена Argon временная.** На странице OpenRouter стоит отметка о скидке 50%. По [обзору Teamday](https://www.teamday.ai/blog/best-ai-models-2026), с 1 декабря 2026 года цена станет 4 / 20 $. Тогда ближайшая замена — `openai/gpt-6.1-sol` за 2 / 10 $.
- **Perplexity Sonar** изначально сделан под поиск ([`perplexity/sonar-pro-search`](https://openrouter.ai/perplexity), 3 / 15 $ плюс 18 $ за 1 000 запросов). Как он видит рунет, неизвестно, поэтому он участвует в прогоне наравне с остальными.

### Прогон-сравнение на этапе 0

Ручные таблицы агентства — готовый эталон: по 30 с лишним объектам известно, какие сигналы и на каких страницах были найдены. К ним добавляем 10 объектов без проблем, чтобы мерить ложные срабатывания.

| Конфигурация | Что проверяет |
| --- | --- |
| Яндекс + своё скачивание + экстрактор | Основной путь |
| Argon + веб-поиск OpenRouter | Хватает ли западного индекса |
| Argon + веб-поиск + `yandex_search` | Сколько добавляет Яндекс в руках модели |
| GPT-6.1 Sol + веб-поиск | Запасной исследователь |
| GPT-6 Astra + веб-поиск | Оправдана ли пятикратная цена |
| Perplexity Sonar Pro Search | Специализированный поисковик |

Что мерим по каждой конфигурации:

- **Полнота** — какая доля известных сигналов найдена.
- **Точность** — какая доля выданных фактов подтверждается цитатой на странице.
- **Свежесть** — найдены ли события последних 14 дней.
- **Ложные срабатывания** — сколько «проблем» найдено у благополучных объектов.
- **Цена и время** на один объект.

Правило решения: основным становится путь с лучшей полнотой при точности не ниже 90%. Astra попадает в продукт, только если даёт на 10 процентных пунктов полноты больше, чем Argon. Прогон стоит примерно 30–50 $ и занимает день. Скрипт прогона остаётся в репозитории и повторяется при выходе новых моделей.

### Правила вызова моделей

- **Структурный вывод.** Экстрактор, разметчик и автор расклада отвечают строго по JSON-схеме: `response_format` с типом `json_schema` и `strict: true`, плюс `provider.require_parameters: true`, чтобы запрос шёл только к провайдерам, которые схему поддерживают.
- **Данные чатов не должны оседать у провайдеров.** Для разметчика и сводчика в каждом запросе стоит `"provider": {"zdr": true, "data_collection": "deny"}`. В презентации агентства обещан «запрет хранения данных на стороне ИИ», и это настройка, которая его выполняет. По [документации](https://openrouter.ai/docs/guides/features/zdr), конечные точки Google Vertex с 18 октября 2026 года под это условие не подходят, поэтому переписку чатов моделям Google не отдаём.
- **Веб-поиск под это условие не попадает.** Сторонние поисковые движки работают по своим правилам. Исследователю нельзя передавать тексты из чатов: только название ЖК, застройщика и вопрос.
- **Пакетный режим.** Ночная разметка сообщений не срочная, поэтому идёт пакетными вариантами моделей за половину цены, например `openai/gpt-6-luna:batch`.
- **Версии промптов.** Каждый промпт — файл `prompts/<роль>/v<N>.md`. Номер версии пишется в `llm_calls`. Менять промпт можно только новой версией.
- **Потолок расходов.** У каждого прогона есть лимит в долларах в конфиге. Шлюз суммирует стоимость из ответов OpenRouter и останавливает прогон при превышении. Второй предохранитель — лимит на самом ключе OpenRouter.
- **Повторы.** При ошибке или невалидном JSON — до трёх попыток с паузой, затем запасная модель роли.

### Правила, которые нельзя нарушать

1. **Ключ объекта — `eisgs_id`.** Сигнал привязывается к корпусу, только если в источнике назван корпус или ID. Иначе он ложится на уровень ЖК. Переносить статус одного корпуса на весь ЖК запрещено.
2. **Сигнал без доказательства не существует.** У сигнала обязательно заполнен `document_id` или `chat_id` и поле `evidence_quote` с дословной цитатой. Код проверяет, что цитата реально есть в тексте документа. Нет совпадения — сигнал отбрасывается.
3. **Дубли склеиваются.** `dedup_key` = тип сигнала + объект + дата события с точностью до недели. Одна новость, перепечатанная десятью сайтами, даёт один сигнал с десятью документами.
4. **Авторы сообщений не хранятся.** В `author_hash` лежит HMAC от ID пользователя с секретной солью. По нему можно посчитать уникальных авторов, но нельзя восстановить человека. Имена, ники и телефоны в базу не пишутся.
5. **Сырые сообщения живут 180 дней.** Потом текст удаляется, остаются разметка и агрегаты. Цитаты, попавшие в расклады, хранятся в `pains.quotes`.
6. **Каждый расклад воспроизводим.** В `briefs.payload` лежат ID сигналов и болей, из которых он собран, и версии промптов и моделей.

## 7. Скоринг, стадии кризиса и раннее предупреждение

Каждый объект получает три оценки от 0 до 100 и из них один класс приоритета. Шкала одна на весь продукт: в ручных таблицах их было четыре, и сравнить объекты между собой было нельзя. Все веса лежат в файле `config/scoring.yaml`, чтобы менять их без правки кода.

### Три оси

| Ось | Что измеряет | Откуда берётся |
| --- | --- | --- |
| Острота | Насколько тяжёл конфликт сейчас | Переносы, надзор, СМИ, суды, чаты |
| Продаваемость | Есть ли кому и зачем продать услугу | Состояние девелопера, признаки спроса, портфель |
| Окно | Насколько сейчас подходящий момент | Дни до триггерной даты, свежесть сигналов |

### Острота: из чего складывается

| Признак | Баллы |
| --- | --- |
| Перенос передачи квартир: до 3 мес / 3–6 / 6–12 / больше 12 | 5 / 10 / 18 / 25 |
| Повторный перенос (второй и далее) | +10 |
| Срок ввода прошёл, РВЭ нет | +15 |
| Надзор: предостережение или проверка | +10 |
| Прокуратура или Следственный комитет | +15 |
| Публикация в региональном СМИ за 60 дней | +8 |
| Публикация в федеральном СМИ за 60 дней | +15 |
| Иски покупателей: от 10 дел | +10 |
| Чат: конфликтные темы больше 25% сообщений за 30 дней | +10 |
| Чат: шаблон коллективной жалобы или сбор подписей | +10 |
| Чат: инициативная группа, отдельный «чат без застройщика» | +10 |
| Чат: подготовка акции, пикета, обращения в СМИ | +15 |

Сумма умножается на коэффициент масштаба: 0,8 для дома до 150 квартир, 1,0 для 150–500, 1,2 для более 500. Итог обрезается на 100.

### Продаваемость: из чего складывается

| Признак | Баллы |
| --- | --- |
| Застройщик действует и платёжеспособен | 40 (база) |
| Банкротство, достройка третьей стороной, спор о том, кто отвечает за проект | вместо базы 10 и метка «сложный заказчик» |
| Понятен адресат: есть PR, клиентский сервис, публичные руководители | +15 |
| Девелопер публично реагирует: комментирует, проводит встречи | +10 |
| Признаки спроса: вакансии в PR или клиентском сервисе, тендеры на мониторинг и репутацию | +15 |
| У девелопера ещё три и более объекта в стройке (шанс на портфельный контракт) | +10 |
| Тёплый контакт или бывший клиент агентства | +10 |
| Известно, что уже работает другое агентство | −15 |
| Девелопер в стоп-листе | объект исключается из дайджеста |

### Окно: из чего складывается

| Ситуация | Баллы |
| --- | --- |
| До срока передачи или ввода 0–90 дней | 100 |
| До срока 91–180 дней | 60 |
| До срока больше 180 дней | 30 |
| Срок прошёл меньше 60 дней назад | 90 |
| Срок прошёл 60–180 дней назад | 70 |
| Срок прошёл больше 180 дней назад | 50 |
| Последний сигнал старше 60 дней | −20 |

### Класс приоритета

| Класс | Условие | Что это значит для руководителя |
| --- | --- | --- |
| A | Острота от 60, Продаваемость от 50, Окно от 50 | Идти сейчас |
| B | Острота от 40, Продаваемость от 40 | Сильный повод, нужен расклад |
| C | Острота от 60, Продаваемость ниже 40 | Тяжёлый кризис, но продать некому |
| Ранний | Сработало правило раннего предупреждения, Острота ниже 40 | Прийти до кризиса с превентивным предложением |
| Наблюдение | Есть хотя бы один сигнал, остальное не выполнено | В дайджест не попадает, виден в таблице |

В дайджест идут A, B и «Ранний». Класс C показывается одной строкой в конце, без кнопок подключения чатов.

### Стадия кризиса

Шкала взята из презентации агентства, чтобы расклад говорил на том же языке, что и коммерческое предложение.

| Стадия | Признаки в данных |
| --- | --- |
| 0. Предкризис | Сроки сдвинуты или под риском, жалоб мало, публикаций нет |
| 1. Информационный вакуум | Много одинаковых вопросов без ответа, противоречивые ответы сотрудников, нет официальной позиции |
| 2. Самоорганизация | Инициативная группа, лидеры мнений, шаблоны обращений на госпорталы |
| 3. Эскалация | Массовые претензии, жалобы в прокуратуру, коллективные обращения, первые публикации |
| 4. Репутационный кризис | Негатив переносится на другие проекты девелопера, устойчивый фон в СМИ |

Отдельно ставится **тип ситуации**: «сроки» (дом строится), «приёмка» (идёт передача ключей), «после заселения» (дефекты, инженерия, спор с УК). От типа зависит, какие офферы подходят и кто заказчик.

### Правила раннего предупреждения

Считаются кодом по данным ЕИСЖС, без модели. Каждое сработавшее правило создаёт сигнал типа «ранний».

| Правило | Условие |
| --- | --- |
| R1. Не успевают | До планового ввода 6 месяцев и меньше, готовность ниже 70%. Или 3 месяца и меньше, готовность ниже 85% |
| R2. Сжимается запас | Ввод перенесён, передача нет, между вводом и передачей осталось меньше 4 месяцев |
| R3. Срок прошёл | Плановый ввод был 30 и более дней назад, РВЭ в реестре нет |
| R4. Риск повторного переноса | Перенос уже был, до нового срока 90 дней и меньше |
| R5. Стройка стоит | Готовность выросла меньше чем на 3 процентных пункта за 60 дней, до ввода меньше года |
| R6. Портфельный риск | У застройщика больше половины строящейся площади с переносами, и срок этого дома в ближайшие два квартала |
| R7. Надзор раньше переноса | Есть предостережение надзора, переноса в декларации ещё нет |

Пороги в R1 и R5 стартовые. После этапа 1 их нужно откалибровать на истории: взять дома, где перенос случился, и посмотреть, какие значения были за полгода до него.

### Сила доказательства и уверенность

У каждого сигнала есть класс источника: **A** — официальный реестр или орган власти, **B** — редакционное СМИ, **C** — отзывы, соцсети, чаты. Уверенность по объекту «высокая», если есть сигнал класса A и независимый от него сигнал класса B или C. «Средняя» — один класс A или два независимых B. «Низкая» — только C. Объекты с низкой уверенностью в класс A не попадают.

### Обратная связь

Кнопка «Не интересно» спрашивает причину одним нажатием: «уже клиент», «некому продавать», «слишком мелко», «данные неверные», «другое». Причины копятся в таблице `feedback`. Раз в месяц оператор смотрит распределение и правит веса вручную. Автоматическое обучение на двух пользователях не нужно: данных мало, а ручная правка прозрачнее.

## 8. Чаты: поиск, подключение, чтение

Чаты читает отдельный рабочий аккаунт Telegram через библиотеку Telethon. Бот чужие чаты читать не может: ботов в группы добавляют только администраторы. Три жёстких правила: только открытые чаты, не больше пяти вступлений в сутки, аккаунт никогда ничего не пишет.

### Где сейчас живут чаты жителей

- **Строящиеся дома.** Чаты дольщиков — в основном Telegram. Это главный сегмент продукта, и он покрывается полностью.
- **Заселённые дома.** 16 декабря 2025 года Госдума приняла закон, по которому управляющие и ресурсоснабжающие организации обязаны общаться с жильцами через национальный мессенджер; СМИ пишут о переносе домовых чатов в MAX ([3DNews](https://3dnews.ru/1134012), [Код Дурова](https://kod.ru/gosduma-zakon-o-chatah-v-max)). Официальные чаты УК уходят туда. Собственные чаты жителей, по оценке юриста в [Новой газете Европа](https://novayagazeta.eu/articles/2025/12/17/domovye-chaty-pereezzhaiut-v-max), остаются добровольными.
- **Что из этого следует.** Первая версия работает только с Telegram. По ситуациям «после заселения» покрытие будет неполным. MAX вынесен на этап 3: сначала нужно выяснить, есть ли у него законный способ читать открытые чаты программно. ВКонтакте закрывается через официальный API: стены и комментарии групп ЖК.

### Как система ищет чаты

| Способ | Как работает |
| --- | --- |
| Ссылки в уже собранных документах | Поиск адресов вида `t.me/...` в текстах статей и на сайте ЖК |
| Яндекс | Запросы `ЖК {название} чат телеграм`, `ЖК {название} чат дольщиков`, `ЖК {название} соседи чат` |
| Поиск внутри Telegram | Рабочий аккаунт ищет по названию ЖК и его вариантам. Не больше 20 поисков в сутки |
| Официальный канал застройщика или ЖК | У канала может быть привязанная группа обсуждений; она читается как открытый чат |
| Группы ЖК ВКонтакте | В описании и меню группы часто лежит ссылка на чат в Telegram |
| Ручное добавление | Руководитель или оператор присылает боту ссылку на чат и название ЖК |

По каждому кандидату система, не вступая, запрашивает карточку чата: название, описание, число участников, нужна ли заявка на вступление. Дешёвая модель по названию и описанию определяет вид чата и уверенность, что это тот самый ЖК. При уверенности ниже 0,8 связь подтверждает оператор. В дайджест попадают чаты от 50 участников; барахолки и чаты объявлений отбрасываются.

### Что считаем открытым чатом

| Ситуация | Решение |
| --- | --- |
| Публичная группа с именем вида `@...` | Открытый. История читается без вступления, аккаунт в списке участников не появляется |
| Ссылка-приглашение опубликована в открытом доступе, вход без одобрения | Открытый. Нужно вступить |
| При входе бот-защита от спама просит нажать кнопку или решить пример | Открытый. Вступает оператор вручную |
| Вход по заявке, администратор спрашивает квартиру или ДДУ | Закрытый. Не вступаем |
| В правилах чата написано «только для собственников» | Закрытый. Не вступаем, а если уже вошли — выходим |
| Ссылку можно получить, только представившись жителем | Закрытый. Не вступаем |

Принцип один: аккаунт не выдаёт себя за жителя ни словом, ни анкетой. Если для входа это требуется, чат не наш. Такие чаты помечаются «закрытый» и показываются в раскладе строкой «есть закрытый чат на N участников, не читаем»: сам факт его существования — признак самоорганизации.

### Рабочий аккаунт

- **Отдельный номер**, оформленный на агентство или оператора. Личные аккаунты руководителей и сотрудников не используются. На старте один аккаунт и один запасной.
- **Нейтральный профиль:** обычное имя, без упоминания агентства и без легенды «я дольщик».
- **Возраст:** аккаунт должен прожить 2–4 недели обычной жизнью до подключения к API. Свежие аккаунты блокируют чаще.
- **Ключи API** (`api_id`, `api_hash`) выдаются на my.telegram.org на этот же номер.
- **Двухфакторная защита** включена. Файл сессии лежит только на сервере, в зашифрованном виде. Утечка сессии равна утечке аккаунта.
- **Один аккаунт — один постоянный адрес сервера.**

### Лимиты

| Что | Лимит на старте |
| --- | --- |
| Вступлений в сутки на аккаунт | 5 |
| Пауза между вступлениями | 20–40 минут, случайно |
| Вступлений в неделю на аккаунт | 25 |
| Чатов на аккаунте одновременно | 250 |
| Поисков внутри Telegram в сутки | 20 |
| Пауза между запросами истории | 1–2 секунды |
| Глубина первой загрузки | 90 дней или 60 000 сообщений, что наступит раньше |

Если Telegram отвечает ошибкой ожидания (FloodWait), аккаунт ждёт указанное время плюс запас. При ожидании больше часа вступления останавливаются на сутки, оператор получает сообщение. Из чатов по объектам со статусом «Закрыт» или «Не интересно» аккаунт выходит через 30 дней.

### Что аккаунт не делает никогда

- Не пишет сообщения, не ставит реакции, не голосует в опросах.
- Не пишет участникам в личные сообщения.
- Не скачивает список участников, фото, файлы и голосовые.
- Не сохраняет имена, ники и телефоны.

### Загрузка и разметка

1. **Первая загрузка.** История за 90 дней пачками по 100 сообщений. Сохраняются текст, дата, хеш автора, связь «ответ на», число реакций. Чат на 60 000 сообщений грузится около 15 минут.
2. **Ночное дочитывание.** Каждую ночь забирается всё новее `last_message_id`.
3. **Отсев кодом.** Убираются служебные сообщения, стикеры, пустые тексты, точные повторы.
4. **Разметка моделью.** Сообщения идут пачками по 150–200 вместе с тем, на что они отвечают. На каждое модель возвращает: относится ли к делу, код темы, тон от −2 до +2, кому адресовано, флаги.
5. **Агрегаты.** Код считает по дням и темам: число сообщений, число уникальных авторов, долю негатива.
6. **Сборка болей.** Сводчик получает главные темы с цифрами и по 40–60 сообщений на тему. Он формулирует боль, описывает её и выбирает 2–3 дословные цитаты. Код проверяет, что цитаты есть в базе, и вырезает из них имена, номера квартир и телефоны.

### Словарь тем

| Группа | Темы |
| --- | --- |
| Сроки | Перенос сроков; выдача ключей; ход стройки, «стройка стоит» |
| Деньги | Неустойка и компенсации; доплаты и обмеры; ипотека и аренда на время задержки |
| Качество | Приёмка и дефекты; отделка; инженерия (отопление, вода, лифты, канализация, электричество); протечки |
| Управление домом | Тарифы УК; качество работы УК; смена УК и собрания собственников; охрана и доступ |
| Территория | Парковка; благоустройство; обещанная инфраструктура (школа, сад, дороги) |
| Коммуникация застройщика | Нет ответов; разные ответы от разных сотрудников; грубость и отписки |
| Действия жителей | Жалобы в органы власти; суд; обращение в СМИ; акция или пикет; инициативная группа |
| Не по делу | Объявления; бытовой разговор; позитив |

Флаги сообщения: «вопрос без ответа», «призыв к действию», «шаблон жалобы», «угроза судом», «упоминание СМИ», «ссылка на другой чат», «ответ представителя застройщика».

### Что из чата попадает в расклад

- Сообщений и уникальных авторов в день, среднее за 30 дней.
- Доля конфликтных сообщений и её изменение: последние 14 дней против предыдущих 14.
- Пять главных тем с долями и стрелкой тренда.
- Доля вопросов к застройщику, оставшихся без ответа.
- **Концентрация:** сколько авторов дают половину конфликтных сообщений. Пять человек — это узкий актив, пятьдесят — широкое недовольство. Число без имён.
- Признаки самоорганизации с датами: шаблон жалобы, сбор подписей, отдельный чат, подготовка акции.
- Две-три цитаты на каждую боль, без автора, с датой.

## 9. Расклад и библиотека офферов

УТП не сочиняется моделью, а собирается из библиотеки услуг агентства: код подбирает услуги под найденные боли, модель только пишет текст вокруг них. Поэтому в раскладе не может появиться услуга, которой агентство не оказывает, или факт, которого нет в базе.

### Путь от данных к PDF

1. **Сбор.** Код собирает по объекту все сигналы, боли, цифры чатов, ближайшие даты.
2. **Подбор офферов.** Код выбирает из библиотеки одно главное предложение и до двух дополняющих.
3. **Подбор кейса.** Код ищет в базе кейсов агентства похожий по типу ситуации и стадии.
4. **Текст.** Модель-автор получает только эти данные и заполняет структуру расклада в JSON.
5. **Проверка кодом.** Даты, числа, цитаты и ссылки сверяются с базой.
6. **Проверка второй моделью.** Модель другого семейства ищет утверждения без опоры на сигнал.
7. **Вёрстка.** Шаблон превращает JSON в PDF на две страницы.
8. **Доставка.** Бот присылает краткую карточку и PDF.

### Библиотека офферов

Библиотека — файл `config/offers.yaml`. Стартовый набор собран из презентации агентства и листов «Продукты и KPI» из ручных таблиц. Руководители должны его вычитать и поправить формулировки до запуска: это их коммерческий язык.

| Код | Оффер | Когда предлагать | На какие боли отвечает |
| --- | --- | --- | --- |
| O1 | Антикризисная диагностика объекта | Стадии 0–3, любой тип. Входной продукт | Любые; когда картина неполная |
| O2 | Предкризисная программа при переносе сроков | Стадия 0, класс «Ранний» | Перенос сроков, риск повторного переноса |
| O3 | Единая позиция, Q&A и речевые модули для сотрудников | Стадии 1–2 | Нет ответов; разные ответы сотрудников |
| O4 | Штаб завершения строительства и выдачи ключей | Стадии 1–3, типы «сроки» и «приёмка» | Выдача ключей; ход стройки; приёмка |
| O5 | Диалог с инициативной группой: встречи, экскурсии на стройку, модератор | Стадии 2–3 | Инициативная группа; жалобы в органы власти; подготовка акции |
| O6 | Претензионная коммуникация, согласованная с юристами | Стадии 2–4 | Неустойка; суд; массовые претензии |
| O7 | Сервис по инженерным претензиям: общий штаб застройщика и УК | Тип «после заселения» | Инженерия; протечки; качество работы УК |
| O8 | Коммуникации при смене застройщика или инвестора | Есть сигнал «смена собственника» | Неясно, кто отвечает за обязательства |
| O9 | Работа с отзывами на площадках | Любая стадия, есть сигналы класса C из отзывов | Негатив в отзывах |
| O10 | Взаимодействие с органами власти и официальные ответы | Есть сигналы надзора или прокуратуры | Проверки, предостережения, коллективные обращения |
| O11 | Антикризисное сопровождение в СМИ | Стадии 3–4 | Публикации, запросы журналистов |
| O12 | Ежедневный мониторинг чатов и инфополя | Стадии 1–4, как дополнение | Любые; нужен контроль динамики |

Один оффер в файле выглядит так:

```yaml
- code: O3
  name: Единая позиция и речевые модули
  stages: [1, 2]
  situation_types: [сроки, приёмка, после_заселения]
  pain_topics: [нет_ответов, разные_ответы, перенос_сроков]
  promise: Покупатели получают один и тот же ответ от любого сотрудника
  deliverables:
    - Q&A по острым вопросам объекта
    - Речевые модули для офиса продаж, колл-центра и стройплощадки
    - Тренинг по работе с негативом
  pilot_30d: Один ЖК, Q&A из 20 вопросов, обучение двух смен сотрудников
  kpis:
    - Доля повторных вопросов в чате
    - Доля вопросов без ответа
  buyer_roles: [руководитель клиентского сервиса, PR-директор]
  not_when: [застройщик_банкрот]
```

**Чего в библиотеке нет.** Услуг, построенных на вымышленных отзывах, скрытом влиянии на инициативные группы или сокрытии недостатков. Это правило уже записано в методике ручных таблиц агентства («Правовая корректность»), продукт его просто наследует.

### Как код подбирает офферы

1. Оставить офферы, у которых подходят стадия и тип ситуации. Убрать те, у кого сработало `not_when`.
2. Посчитать каждому очки: за каждую боль объекта, которая есть в `pain_topics` оффера, прибавить вес боли. Вес боли — её доля в конфликтных сообщениях или, если чатов нет, сумма баллов её сигналов.
3. Оффер с максимумом очков — главный. Следующие два — дополняющие, если они закрывают боли, не закрытые главным.
4. Если чаты не подключены или уверенность низкая, главным ставится O1 (диагностика): честнее продавать исследование, чем решение недоказанной проблемы.
5. Роли адресатов берутся из главного оффера.

### Структура расклада

Это схема `briefs.payload`. Модель-автор заполняет только поля, помеченные «текст»; остальное подставляет код.

| Блок | Поля | Кто заполняет |
| --- | --- | --- |
| Шапка | ЖК, девелопер, юрлицо, регион, корпуса, класс, три оценки, стадия, тип, уверенность, версия, дата | Код |
| Сроки | По каждому корпусу: ввод был и стал, передача была и стала, число переносов, РВЭ | Код |
| Суть | Один абзац до 400 знаков: что происходит на объекте | Текст |
| Хроника | 4–6 событий: дата, одно предложение, номер источника | Код выбирает сигналы, текст формулирует модель |
| Боли | 3–4 боли: заголовок, описание до 250 знаков, цифры (сообщений и авторов за 30 дней, тренд), 1–2 цитаты | Цифры и цитаты — код, описание — текст |
| Чаты | Сколько чатов читаем, участников, сообщений в день, доля конфликта, концентрация, закрытые чаты | Код |
| Ближайшие даты | До 3 дат: что наступает и чем грозит | Даты — код, пояснение — текст |
| УТП | Заголовок до 140 знаков; «почему сейчас» до 250 знаков | Текст |
| Главное предложение | Код оффера; 3–4 пункта «что делаем», каждый со ссылкой на боль, которую закрывает | Оффер — код, пункты — текст на основе `deliverables` |
| Дополняющие | До 2 офферов, по одной строке | Код и текст |
| Пилот на 30 дней | Объём, результаты, 2–3 показателя | Из оффера, модель подставляет название ЖК и корпуса |
| Кому продавать | Роли; имена только из публичных источников со ссылкой | Код и исследователь |
| Похожий кейс | Одна-две строки из базы кейсов | Код |
| Стоп-вопросы | 2–4 вещи, которые нужно проверить до КП | Код строит из пробелов в данных, модель формулирует |
| Источники | Нумерованный список: название, дата, класс, ссылка | Код |
| Ограничения | Чего в данных нет: чаты не подключены, есть закрытый чат, источник не обновлялся | Код |

### Правила для модели-автора

- Писать только то, что есть во входных данных. Никаких фактов «из общих знаний» о девелопере.
- Каждое утверждение о событии несёт номер источника.
- Различать корпус и ЖК. Если факт про корпус 3, нельзя писать «в ЖК перенесли сроки».
- Различать перенос ввода, просрочку по ДДУ и дефекты после ввода. Это три разные вещи.
- Нейтральный тон. Не «застройщик сорвал сроки», а «срок передачи перенесён с … на …». Слова жителей приводятся как слова жителей: «по сообщениям в чате».
- Каждый пункт предложения привязан к конкретной боли этого объекта. Пункт, который подошёл бы любому ЖК, вычёркивается.
- Соблюдать лимиты знаков: иначе текст не влезет в вёрстку.

### Проверка перед отправкой

**Код проверяет:**

- все даты и числа из текста есть во входных данных;
- каждая цитата дословно находится в базе;
- каждый номер источника существует;
- в тексте нет ников, телефонов, номеров квартир;
- все поля укладываются в лимиты знаков.

**Вторая модель проверяет:**

- подтверждает ли указанный источник именно то, что написано;
- не смешаны ли корпуса, очереди, разные ЖК с похожими названиями, разные застройщики;
- не подано ли старое как текущее: сигналы старше 60 дней помечаются «требует перепроверки»;
- нет ли обвинений, поданных как установленный факт;
- отвечает ли каждое предложение на боль из списка.

Итог проверки — один из трёх: «прошло», «исправить» (автор переписывает один раз по замечаниям), «на ручной разбор» (расклад уходит оператору, руководителям не отправляется). На PDF стоит отметка «Проверка: автоматическая» или «Проверено оператором».

### Версия для клиента

Кнопка «Готовим КП» собирает одностраничный PDF для девелопера. Отличия от внутреннего расклада:

- нет оценок, класса, блоков «кому продавать» и «стоп-вопросы»;
- нет дословных цитат из чатов, только темы и цифры: по дословной цитате автора легко найти поиском по чату;
- тон обращён к девелоперу: «что видно в открытом поле по вашему объекту», затем предложение и пилот.

Эта версия делается на этапе 3 и всегда проходит через человека перед отправкой.

## 10. Telegram-бот: сценарии и экраны

Бот — единственное место, где руководители что-то нажимают. Он живёт в закрытой группе «Радар», куда входят оба руководителя, оператор и сам бот. Группа удобнее двух личных чатов: решение одного сразу видит второй, и под карточкой объекта можно обменяться парой слов. Названия ЖК и цифры в макетах ниже условные.

### Общие правила

- **Доступ.** Бот отвечает только в группе с заданным ID и только пользователям из таблицы `users`. Любому другому он не отвечает вообще, а оператор получает сообщение о попытке.
- **Один объект — одно сообщение** со своими кнопками. Длина сообщения до 1 200 знаков: должно читаться с телефона без прокрутки.
- **Класс виден цветом.** Перед названием стоит цветной квадрат: красный для A, оранжевый для B, жёлтый для «Ранний», серый для C. В макетах ниже он показан как `[A]`.
- **Нажатие меняет сообщение.** После решения кнопки исчезают, внизу появляется строка «Решение: подключить чаты · Имя · 10:42». Второй руководитель видит результат, а не кнопки.
- **Тишина.** С 21:00 до 09:00 по Москве бот не пишет ничего. Сигналы копятся до утра.
- **Запасной канал.** Telegram в России с февраля 2026 года замедляется и работает с перебоями ([info24.ru, 9 ноября 2026](https://info24.ru/news/pochemu-telegram-ne-rabotaet-segodnya-9-noyabrya-proksi-poslednie-novosti-gde-sboj.html)). Поэтому дайджест и каждый PDF дублируются на почту руководителей. Кнопок в письме нет, но прочитать можно всегда.

### Команды

| Команда | Кто | Что делает |
| --- | --- | --- |
| Название ЖК или застройщика обычным текстом | Все | Ищет в реестре с учётом опечаток, предлагает до пяти совпадений кнопками, показывает карточку |
| `/top` | Все | Десять лучших объектов по текущему скорингу |
| `/inwork` | Все | Объекты в работе со статусами |
| `/check название` | Все | Внеплановая проверка объекта сейчас; ответ через 10–15 минут |
| `/addchat ссылка` | Все | Добавляет чат вручную, спрашивает, к какому ЖК он относится |
| `/stop название` | Руководители | Добавляет девелопера в стоп-лист, с подтверждением |
| `/help` | Все | Краткая памятка |
| `/queue` | Оператор | Очередь вступления; чаты, где нужна ручная капча |
| `/review` | Оператор | Расклады, отправленные на ручной разбор; спорные привязки чатов к ЖК |
| `/status` | Оператор | Последние прогоны, состояние источников, расходы за неделю и месяц |
| `/pause`, `/resume` | Оператор | Останавливает и возобновляет прогоны |

Команды оператора работают в личном чате с ботом, чтобы не засорять группу. Туда же приходят служебные сообщения: источник не отвечает, Telegram просит подождать, превышен бюджет, прогон упал.

### Технические решения

- Библиотека aiogram 3, получение обновлений опросом (long polling). Входящих портов на сервере открывать не нужно.
- Разметка сообщений HTML. Данные кнопки в формате `действие:id_объекта`, не длиннее 64 байт.
- Каждое нажатие пишется в `feedback` и меняет `objects.status`. Повторное нажатие ничего не ломает: второй человек видит всплывающую подсказку «Уже решено».
- PDF отправляется как документ, его `file_id` сохраняется, чтобы повторно не загружать.
- Имя файла: `Расклад_Пример-Парк_к3-4_2026-11-12_v1.pdf`.

Таблица — витрина реестра: восемь листов: шесть система перезаписывает после каждого прогона, два («Стоп-лист» и «Заметки») ведут руководители. Решения принимаются в боте, в таблице только смотрят, фильтруют и сортируют.

| Воронка | Один объект, взятый в работу | Система |

| Справка | Легенда: классы, стадии, цвета, дата последнего обновления | Система |

### Правила работы с таблицей

- **Системные листы защищены от правки.** Всё, что человек впишет в них руками, сотрётся при следующем обновлении. Для свободных заметок — отдельный лист «Заметки», его система не трогает.
- **Стоп-лист читается перед каждым прогоном.** Название сопоставляется с реестром с учётом опечаток. Если совпадения нет, оператор получает вопрос «кого имели в виду».
- **Обновление пакетом.** Один запрос на лист, весь диапазон целиком. Так не упираемся в лимиты Google Sheets API.
- **Ссылка на расклад** ведёт на сообщение с PDF в группе «Радар». Откроется только у участников группы, и это хорошо: расклады не лежат в облаке по открытой ссылке.
- **Доступ.** Таблицу создаёт агентство на своём аккаунте и даёт права редактора сервисному аккаунту системы. Доступ «по ссылке» выключен.

На схеме — расположение блоков, без дизайна. Бирюзовая плашка на второй странице — единственный крупный цветовой акцент документа: взгляд должен приходить на УТП.

| Шапка | Название ЖК крупно, под ним корпуса, девелопер, юрлицо, регион. Справа класс, стадия, дата и версия | Тёмно-зелёная полоса на всю ширину, белый текст. Класс — буква в цветном квадрате |
| Показатели | Острота, Продаваемость, Окно, Уверенность | Четыре плитки: число крупно, подпись мелко |

| Ближайшие даты | До трёх дат с пояснением | Дата, рядом «через 51 день» оранжевым |

| Хроника | 4–6 событий | Горизонтальная линия времени с точками; под точкой дата, одна строка, номер источника |
| Подвал | Гриф «Внутренний документ, не пересылать», отметка проверки, номер страницы | Мелкий серый текст |

### Страница 2. С чем идти

| Блок | Содержание | Как выглядит |
| --- | --- | --- |
| УТП | Одна фраза до 140 знаков и строка «почему сейчас» | Бирюзовая плашка, крупный белый текст |
| Главное предложение | Название оффера и 3–4 строки «боль → что делаем» | Две колонки со стрелкой между ними. Слева боль теми же словами, что на первой странице |
| Пилот на 30 дней | Объём, результаты, 2–3 показателя | Три колонки на светлом фоне |
| Дополняющие предложения | До двух, по одной строке | Обычный список |
| Кому продавать | Роли; имена только из публичных источников, с номером источника. Ниже похожий кейс | Левая нижняя колонка |
| Перед КП проверить | 2–4 стоп-вопроса и ограничения данных | Правая нижняя колонка, пустые квадраты для галочек |
| Источники | Нумерованный список: название, дата, класс, короткая ссылка | Мелкий текст в две колонки; ссылки кликабельны |

### Стиль

- **Цвета** из презентации агентства: бирюзовый для акцента, тёмно-зелёный для шапки и заголовков, оранжевый только для чисел и сроков, серый для второстепенного. Точные коды цветов взять у дизайнера агентства.
- **Шрифты** встраиваются в PDF. Заголовки — узкий гротеск, похожий на шрифт презентации (например, PT Sans Narrow, бесплатный, с кириллицей). Основной текст — PT Sans, 9,5 пункта.
- **Поля** 14 мм. Сетка в 12 колонок, чтобы блоки обеих страниц выравнивались одинаково.
- **Логотип агентства** в правом нижнем углу второй страницы, мелко.
- Никаких иллюстраций, иконок ради красоты и фоновых карт. Это рабочий документ, а не презентация.

### Как собирается

1. Шаблон — обычная HTML-страница с CSS, лежит в `templates/brief/`. Данные подставляет Jinja2 из `briefs.payload`.
2. Playwright открывает страницу в Chromium и печатает в PDF. Chromium уже есть в проекте для сборщиков, отдельная библиотека для PDF не нужна.
3. Перед печатью код измеряет высоту каждой страницы в браузере. Если содержимое не влезает, убирается последний элемент самого длинного списка (четвёртая боль, шестое событие хроники). Текст не обрезается никогда.
4. Готовый файл кладётся в `data/briefs/`, путь пишется в `briefs.pdf_path`.

### Особые случаи

- **Чаты не подключены.** Блок «Чаты» показывает «не подключены» и сколько найдено. Боли строятся по публикациям и помечены «по открытым источникам». Главное предложение — диагностика.
- **Класс «Ранний».** Вместо болей — блок «Признаки риска» с сработавшими правилами и цифрами. Хроника короткая.
- **Несколько корпусов с разным статусом.** Один расклад на ЖК, в таблице сроков до шести корпусов; если больше — шесть с ближайшими сроками и строка «ещё N корпусов в таблице».
- **Обновление.** Версия 2 и далее показывает в шапке «изменилось с прошлой версии» одной строкой.

### Правила кода

3. **Ответ модели — непроверенные данные.** Он всегда проходит через схему Pydantic. Текст со страниц и из чатов — тоже данные, а не инструкции: в промпте он отделён от указаний модели.
4. **Названий моделей в коде нет.** Только роли; модели — в `config/models.yaml`.
5. **Время в базе — UTC,** на экране — Москва.
6. **Секреты только в `.env`,** в репозиторий не попадают никогда.
7. **Каждое значимое решение** записывается одной строкой в `docs/DECISIONS.md`.

## 14. Инфраструктура и безопасность

Нужны два арендованных сервера и десяток учётных записей в сервисах. Все учётные записи оформляются на агентство, а не на разработчика: продукт должен пережить смену подрядчика.

### Серверы

| Сервер | Где | Мощность | Что на нём |
| --- | --- | --- | --- |
| Основной | Европа: Германия, Финляндия или Нидерланды | 4 ядра, 8 ГБ памяти, 80 ГБ диска, Ubuntu 24.04, постоянный адрес | Четыре контейнера, файлы снимков страниц и PDF |
| Шлюз | Россия, любой крупный хостинг | 1 ядро, 1 ГБ памяти | Только HTTP-прокси |

Между серверами поднимается туннель WireGuard. Прокси слушает только адрес туннеля, из интернета он не виден.

### Где лежит база: решение за юристом

Сообщения жителей могут содержать персональные данные граждан России. Российский закон о персональных данных требует хранить такие данные в базах на территории России. Поэтому адрес базы — это настройка `DATABASE_URL`, а не решение в коде. Я не юрист; выбор варианта должен сделать юрист агентства до начала этапа 2.

| Вариант | Как устроено | Плюс | Минус |
| --- | --- | --- | --- |
| А. Всё в Европе | База рядом с кодом на основном сервере | Проще и быстрее всего | Тексты чатов хранятся за пределами России |
| Б. База в России | Российский сервер берётся мощнее (2 ядра, 4 ГБ, 80 ГБ), на нём PostgreSQL. Код в Европе ходит в базу по туннелю | Сообщения сразу записываются и хранятся в России | Медленнее запросы; передача текстов моделям остаётся трансграничной |

В обоих вариантах действует одно правило: перед отправкой модели из текста сообщения кодом вырезаются телефоны, адреса почты, упоминания через `@` и номера квартир.

### Сеть и доступ

- Бот работает опросом, поэтому наружу открыт только SSH. Вход по ключу, пароли отключены, стоит межсетевой экран и блокировка перебора.
- PostgreSQL слушает только внутреннюю сеть Docker или адрес туннеля.
- Доступ к серверам у двух человек: разработчик и один ответственный в агентстве.
- Диск с базой зашифрован.

### Резервные копии

- Каждую ночь — полная копия базы, зашифрованная, в отдельное хранилище вне сервера.
- Хранятся 14 ежедневных и 8 еженедельных копий.
- Раз в месяц копия разворачивается на тестовой машине. Копия, которую ни разу не восстанавливали, копией не считается.
- Файл сессии Telegram и `.env` хранятся отдельно, в менеджере паролей.

### Наблюдение

Оператор получает сообщение в личный чат с ботом, если:

- недельный прогон не закончился к 08:00 понедельника;
- источник не отвечает два прогона подряд или его страница изменилась так, что разбор ничего не нашёл;
- Telegram попросил подождать больше часа или сессия рабочего аккаунта стала недействительной;
- прогон остановлен по лимиту расходов;
- на счету OpenRouter осталось меньше 20 $ или на счету Yandex Cloud меньше 500 ₽;
- на диске осталось меньше 15% места;
- ночная резервная копия не создана.

В журнал никогда не пишутся тексты сообщений из чатов и секреты. Журнал хранится 30 дней.

## 15. Правовые и репутационные рамки

Главный риск продукта не технический: он читает переписку живых людей и пишет неприятное о компаниях. Ниже — ограничения, которые встроены в продукт, и вопросы, на которые до запуска должен ответить юрист агентства. Этот раздел не заменяет юридическое заключение.

### Что встроено в продукт

| Ограничение | Где закреплено |
| --- | --- |
| Только открытые чаты; аккаунт не выдаёт себя за жителя | Правила очереди вступления, раздел 8 |
| Аккаунт только читает | В коде читателя нет функций отправки |
| Имена, ники, телефоны авторов не хранятся | В схеме базы для них нет полей, только хеш |

| Сырые сообщения удаляются через 180 дней | Еженочная задача очистки |
| Перед отправкой модели из текста вырезаются контакты | Шлюз моделей |
| Модели не хранят переписку | Маршрутизация только на провайдеров без хранения данных, раздел 5 |

### Правила площадок

- **Telegram.** Автоматизация через обычный аккаунт может закончиться ограничением аккаунта. Риск снижают лимиты из раздела 8 и отказ от любых действий, кроме чтения. Запасной аккаунт готовится заранее.
- **Сайты.** Собираются только открытые страницы, без входа под логином и без обхода защиты от роботов. Площадки отзывов массово не скачиваются.
- **ВКонтакте и hh.ru.** Только официальные API в пределах их лимитов.

### Репутация самого агентства

История «агентство читает чаты жителей, чтобы продавать услуги застройщикам» вредна для компании, которая сама занимается репутацией. Чтобы её не возникло:

- расклады помечены «внутренний документ» и живут только в закрытой группе;
- девелоперу показывается только клиентская версия: темы и цифры из открытых источников, без цитат и без указания на конкретных людей;
- в предложениях нет услуг, построенных на скрытом влиянии на жителей (раздел 9);
- во внешних материалах продукт описывается как мониторинг открытых источников, чем он и является.

### Чем управлять расходами

- **Число объектов у исследователя.** Это самая дорогая строка. Десять объектов вместо двадцати снимают около 20 $ в месяц.
- **Пакетный режим для разметки** вдвое снижает расходы на чаты.
- **Отсев кодом до модели.** Чем больше мусора убрано до вызова, тем дешевле.
- **Глубина первой загрузки чата.** 60 дней вместо 90 дают треть экономии на новых чатах.

Команда `/status` показывает оператору расходы по ролям за неделю и месяц, так что отклонение от этой оценки будет видно сразу.

## 19. Риски и открытые вопросы

Два риска могут изменить проект целиком: ЕИСЖС не отдаст данные программно, и открытых чатов у горячих объектов окажется мало. Оба проверяются дёшево и рано, поэтому проверка стоит в этапе 0 и в начале этапа 2.

### Риски

| Риск | Что будет, если случится | Что делаем |
| --- | --- | --- |
| ЕИСЖС не отдаёт карточки домов программно или в них нет готовности | Нет покорпусного реестра; не работают правила R1 и R5 | Проверка на этапе 0. Запасной путь: Playwright; в худшем случае реестр на уровне ЖК по ЕРЗ и переносы из публикаций |
| У горячих объектов нет открытых чатов | Расклад строится только на публикациях, УТП менее точное | В первую неделю этапа 2 посчитать покрытие на 30 объектах из эталонного набора. Главное предложение в таких случаях — диагностика |
| Telegram в России заблокируют полностью | Руководители не смогут пользоваться ботом; жители постепенно уйдут из чатов | Дубль на почту есть с этапа 3. Логика бота отделена от площадки, чтобы интерфейс можно было перенести. Чтение чатов из Европы продолжит работать, пока чаты живы |
| Жители переедут в MAX | Падает покрытие, сначала по заселённым домам | Следить за долей объектов без чатов. На этапе 4 выяснить возможности MAX |
| Рабочий аккаунт Telegram ограничат | Чтение останавливается | Лимиты, чтение публичных групп без вступления, готовый запасной аккаунт |
| Модель ошибается в фактах | Руководитель идёт к девелоперу с неверными данными | Проверка цитат кодом, вторая модель, стоп-вопросы в каждом раскладе, кнопка «Ошибка в данных». Проверка человеком перед КП остаётся обязательной |
| Слишком много неинтересных объектов | Руководители перестают читать дайджест | Не больше восьми объектов в неделю, причины отказов, ежемесячный пересмотр весов |
| Цены моделей вырастут или модель снимут | Растут расходы или падает прогон | Модели в конфиге, запасная на каждую роль, повторяемый прогон-сравнение, потолок на ключе |
| Оплата сервисов из разных стран | OpenRouter нужна нероссийская карта, Yandex Cloud — российское юрлицо | Решить на этапе 0, кто что оплачивает |
| Юрист не согласует хранение переписки | Этап 2 меняется | Вариант Б с базой в России; в крайнем случае хранить только разметку и агрегаты, без текстов |
| Продукт зависит от одного разработчика | При его уходе продукт останавливается | Учётные записи на агентстве, `RUNBOOK.md`, этот документ в репозитории |
